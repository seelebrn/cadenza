🚀 Release runbook

Shipping a new Cadenza build

Every release is built and published automatically by GitHub Actions — Windows, macOS, and Linux installers, all from one push. This page is the exact sequence, written for someone who hasn't used GitHub much before.

Repository: github.com/seelebrn/cadenza

Quick reference already done this before? just the commands:

# 1 — bump the version, then commit it
git add package.json
git commit -m "Bump version to 0.1.1"
git push origin main
# 2 — tag that commit and push the tag: this is what starts the build
git tag v0.1.1
git push origin v0.1.1
# 3 — watch it build, then check the result
github.com/seelebrn/cadenza/actions
github.com/seelebrn/cadenza/releases

Terms used below

Commit
One saved snapshot of changes to the project's files.
Push
Sending commits you've made on your computer up to GitHub.
Tag
A permanent label on one exact commit, marking a version — e.g. v0.1.1. Pushing a tag is what triggers a release build here.
Workflow (GitHub Actions)
An automated recipe that runs on GitHub's own computers. Cadenza has two: CI (checks the code) and Release (builds and publishes installers).
Release
A page on GitHub listing one version's downloadable files — this is what end users actually visit.
Draft
A release only you can see. Cadenza's releases publish immediately now — this used to trip things up, it's already fixed.

Step by step

1

Decide the new version number

Cadenza follows the usual three-number scheme, major.minor.patch (the current release is 0.1.0). Going forward:

— bug fix only → bump the last number: 0.1.1

— new feature, still compatible → bump the middle number: 0.2.0

— something that breaks old projects/behavior → bump the first number: 1.0.0

2

Edit package.json

In the project folder, open package.json and change the "version" field near the top to your new number. This is what every installer file gets named after, so it should always match the tag you're about to create in step 4.

3

Commit and push the version bump

From a terminal, in the project folder:

git add package.json
git commit -m "Bump version to 0.1.1"
git push origin main

This just saves and uploads the version change — nothing builds yet.

4

Create the tag and push it

This is the step that actually starts the release build:

git tag v0.1.1
git push origin v0.1.1
⚠ The tag name needs a v in front and must match the version from step 2 exactly — v0.1.1 for version 0.1.1. git push origin main alone (step 3) does not trigger a build — only pushing the tag itself does.
5

Watch it build

Open github.com/seelebrn/cadenza/actions — near the top of the repo page, it's the tab labeled Actions, next to Code, Issues and Pull requests.

You'll see a new run called Release appear. It checks the code first, then builds Windows, macOS, and Linux versions at the same time — usually 5 to 15 minutes in total.

6

Get the files from the Releases page

Once everything's green, go to github.com/seelebrn/cadenza/releases (also linked from the right-hand sidebar of the repo's main page). Your new version is there with three files attached — a Windows installer/portable .exe, a macOS .dmg/.zip, and a Linux .AppImage. That page is what you'd link anyone to.

Before you tell anyone to download it

Neither Apple nor Microsoft has certified these builds — that costs money (Apple: $99/year) and isn't set up for Cadenza — so both macOS and Windows show a security warning the first time someone opens it. Expected, not a sign anything's actually wrong.

🍎 macOS

"Apple could not verify 'Cadenza' is free of malware…" (or similar wording, depending on macOS version)

Confirmed working, macOS Sequoia: open System Settings → Privacy & Security, scroll down to the line about Cadenza being blocked, click Open Anyway. One-time, per computer. Right-click → Open may also work on older macOS versions, but Settings is the reliable path on current ones.

🪟 Windows

"Windows protected your PC" (SmartScreen)

Click More info, then Run anyway. Also one-time, per computer.

Worth pasting into the release description on GitHub (or wherever you send the link) so people see it before, not after, they get worried:

⚠️ macOS and Windows will show a security warning the first time you open Cadenza — this is because the app isn't (yet) signed by Apple/Microsoft, not because anything's wrong with it.

macOS: System Settings → Privacy & Security → scroll down → "Open Anyway".
Windows: click "More info" → "Run anyway".

Reading the Actions page

success

Green check. That job finished cleanly — nothing to do.

in progress

Yellow/orange, still spinning. Just wait — refresh in a minute or two.

failed

Red ×. Click into that job to see which step failed and why.

If something goes wrong

I pushed but nothing shows up in Actions

Most likely only the commit was pushed, not the tag. git push origin main and git push origin v0.1.1 are two separate commands — both are needed, in that order.

One of the three platform builds failed

Open that job in the Actions run and look for the step with the red ×. Paste that error back — the other two platforms can still succeed and publish independently of one that fails.

I need to redo the same version number

Delete the tag both locally and on GitHub first, then retag once the fix is in: 

git tag -d v0.1.1
git push origin :refs/tags/v0.1.1

Can I just click "Run workflow" instead of tagging?

Yes — Actions → Release → Run workflow button. It builds and publishes for real, same as a tag push, so treat it the same way rather than as a safe test run.

Specific to seelebrn/cadenza — the exact commands assume you're already in the project folder with git set up.
